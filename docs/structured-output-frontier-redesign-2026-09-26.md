# 结构化输出高难题改造方案：从格式合规转向有依据的值与约束交互

日期：2026-09-26。本文是下一轮实施规格，不改变已发布题面、分数或题库版本，也没有新增模型调用。

## 一、结论和证据边界

正式结构化输出题现有 60 道：旧规则题 46 道，新契约题 14 道，另有 19 道显式开发题。14 道新题的七题族单题抽样，Nerkyor 为 5/7、DeepSeek 为 7/7；前一批开发题为 16/19、18/19。当前新题的强模型天花板仍明显。14 道新题只有 10 道 JSON、1 道 CSV、1 道 XML、2 道 SVG；已知正确目标的深度多在 2–5 层，单题一般只有一个短输入块，许多题是同一程序模板换值。

**关键诊断：题面中的 Schema 约束复杂度、任务的事实判断难度、输出格式难度是三条不同轴。** 当前题库在第一轴已经开始使用标准验证器，在第三轴有解析和渲染；第二轴仍以简单映射为主。给题面再加一层 JSON 或多几个字段，不会自动提高有依据的值判断难度。

## 二、从原始研究提炼出的设计原则

| 一手研究 | 其实际测量点 | 对 zxbench 的取舍 |
|---|---|---|
| [SchemaBench](https://arxiv.org/html/2502.18878) | 从 SchemaStore/GitHub 收集真实 Schema，分 Complex、Custom、Escape；另设 schema-constrained reasoning，要求内容答案与 Schema 同时正确。其 Escape 类比单纯结构更难。 | 使用**可到达的真实条件分支**和嵌套转义，并将同一事实任务的简单输出与复杂输出配对；拒绝仅堆很长但允许走简单分支的 Schema。 |
| [JSONSchemaBench](https://arxiv.org/html/2501.10868) | 真实 Schema 来源和复杂度分层，区分引擎是否接受 Schema 与输出是否真的合规；官方 JSON Schema 测试套件用于检查实现覆盖。 | 保留裁判准入测试和明确方言。官方套件通过数**不作为题目难度证据**；不得把受限解码引擎的覆盖率当模型能力。 |
| [StructEval](https://arxiv.org/html/2505.20139) | 分生成与格式转换、文本解析与视觉渲染；论文报告若干常用 JSON/CSV/YAML/HTML 任务已超过 90%，文本到 SVG/Mermaid/TOML 和部分跨格式任务仍有难度。 | 减少仅做同值搬运的转换；保留多格式基础锚点，难题要求先完成信息整合再编码，图形题需判可见内容和数据映射。 |
| [DeepJSONEval](https://arxiv.org/html/2509.25922) | 从多文档低密度内容提取到 3–7 层 JSON，分离语法、字段与整题正确；有人工质量检查。 | 采用多段来源、实体/时间关联、必要的嵌套结构；控制输出长度，不能用无意义深度充当能力难度。 |
| [Structured Output Benchmark 2026](https://arxiv.org/html/2604.25359) | 给模型文本化的来源内容、问题及 Schema，比较逐叶路径的值正确率与整题全对率。论文报告结构合规明显高于值正确率；文本来源包含多跳事实与干扰段。 | 把**来源支持的字段值**设为挑战轨核心，独立报告路径覆盖、类型、逐叶值、无依据字段和整题全对；保留证据定位。 |
| [ExtractBench 2026](https://arxiv.org/abs/2607.29677) | 企业文档的字段值、记录完整性、来源证据和成本分别测量。 | 用真实业务形状的表格/更正通知/事件日志，要求完整列表与来源证据；不把长文档截断混入结构能力结论。 |
| [LiveBench](https://arxiv.org/abs/2406.19314) | 使用更新的、可客观评分的题目控制污染和饱和。 | 固定锚点与轮换挑战题并存；保留历史题包版本，不靠改旧题面制造新的“历史分”。 |

这些论文的历史模型分数不能移植为本地模型目标。尤其 JSONSchemaBench、SchemaBench 的 Schema 复杂性不自动代表**给定来源下的值**会错；StructEval 的关键词或视觉问答评分也不能直接替代 zxbench 的确定性业务断言。

## 三、具体题目规格

### 1. 四类真正需要推导的来源任务

首批写 **8 道开发候选，四类各两道**；另冻结每类一份不同来源的留出题（共 4 道）。先用现有两模型筛查开发题，留出题仅用于已锁定的题组，不能反复试错。

1. **多来源事实合并**：给事件记录、后一份修订通知、权限或状态表。输出每个实体的最终状态与事实来源 ID。至少 2 次跨段关联，含相似名称、被撤回值与一个应省略字段。优先级、冲突处理、时区和缺值规则在题面说明。
2. **条件结构与内容耦合**：在上项事实基础上选择 JSON Schema 的不同分支；条件决定必需字段及字段类型，`oneOf`/`dependentRequired`/`unevaluatedProperties` 组成真实交互。每个预定分支都必须有合法见证和针对性错误样本，避免模型靠省略困难字段取巧。
3. **版本迁移与多步编辑**：输入旧版配置、迁移规则和更正记录；要求保留未变字段，区分 `null`、空串、缺键、前导零字符串。后一步规则依赖前一步形成的状态；答案经独立迁移器生成，题面只提供规则和输入。
4. **有依据的跨格式输出**：先从两个来源筛选并合并记录，再生成 CSV/XML/YAML/TOML 或可渲染图。格式本身可机械解析，但值、顺序、数量和可见图形须与来源吻合。与一份简单 JSON 任务配对，度量格式约束造成的额外损失。

每题的非格式负担控制在约 2–4 个可说明的依赖跳数、8–20 个关键叶值，输出规模不靠大量重复行制造失败。这些范围是**设计起点**，不是已经验证的难度等级。记录 `source_count`、独立依赖跳数、相互作用的条件数、目标叶值数、输出字数、Schema 分支覆盖和干扰项类型；筛查之后才标注实测难度。

### 2. 一个可直接制作的样题族

来源 A 是五条订单事件，来源 B 是两条后来发布的更正，来源 C 是账户权限与产品映射。题面明确：更正按目标事件 ID 覆盖原值；已撤销事件不计入余额；权限在更正后的账户状态上判定；同名产品以 SKU 区分；金额与状态由已确定的事件推导。输出为含 `accounts[].orders[]` 的 JSON：每单有最终状态、净额、异常标记及 `sourceIds`。Schema 对退款、拒绝、完成三个分支设不同必需字段，禁止额外字段。

同一来源做简单任务（只输出每单状态和金额）与挑战任务（嵌套 Schema、证据、条件字段）。两者共享事实，不共享输出格式。正确答案由事件重放程序产生，再由另一种实现或人工抽查；模型生成的另一份合法 JSON 只要符合语义谓词也应通过。定向反例至少覆盖：使用被撤销金额、把缺值写成 null、把同名不同 SKU 合并、给拒绝分支多余字段、漏掉最后更正来源。

### 3. Schema 来源和留出隔离

从可合法使用的 SchemaStore/GitHub 等真实 Schema 中挑可独立冻结的片段，保留原仓库、版本、许可证、文件 SHA、声明方言、引用闭包和结构来源。题目中的业务实例是**本地派生**，不冒称官方题目。当前 Ajv 对已知有问题的 `if/else` 无 `then` 及动态引用形状继续在准入阶段拒绝；受支持子集先于模型调用确认。

开发与留出按**来源文档组、Schema 家族和规则模板**分开，不能只换姓名、数字或随机种子。留出金标与行为用例移出 `/api/scenarios` 返回的 `requirements.assertions.expected`；题库只留不可逆哈希及服务器端私有 oracle 引用。当前评分器把期望值存在题目 `requirements` 并由题目 API 返回，适合本地确定性题，但不具备真正盲测隔离。新版本不得把测试用例或结果通过题目接口暴露给被测端。

## 四、评分器 v4 规格

旧 `structured_contract_v1/v2/v3` 不改写；新题使用单独版本并保持原始答案、题包哈希可追溯。

1. **硬门槛**：完整原文可解析、声明的 JSON Schema/目标格式可验证、目标内容谓词通过，整题成功才为 100；环境或裁判缺失记未测，不给模型 0。对图形仍要求目标渲染成功。
2. **分层诊断**：另外保存格式成功、Schema 成功、目标路径召回、类型正确、已匹配路径的来源值正确、额外路径/无依据值、证据引用有效、整题全对。精确 ID、数字、转义不做宽松 token F1；自由文本如需多种等价值，先在题面和 oracle 中列明允许的规范化规则。
3. **按来源检查值**：每个关键叶值的 oracle 包含值、来源记录 ID、允许的规范化与是否可省略。数组若题意无顺序要求，用稳定主键匹配；若题面要求时序，按索引比对。外部事实不靠 AI Judge 临时猜测。
4. **结构与内容分开**：保留同源简单输出与挑战输出对照。报告 `简单任务值准确率`、`挑战任务值准确率`、`挑战格式/Schema 合规率`、`整题全对率` 和配对成功差；这能区分来源理解失败与格式规划失败。题族等权汇总，成对变体先在题族内汇总。
5. **判题器准入**：每题至少一份合法见证、每个可达分支一份见证、针对关键语义的一类一错反例、等价合法写法样例；Python/jsonschema 与 Ajv 在实际用到的方言/特性上交叉核对。只执行涉及的检查，避免全套无关测试。

## 五、题量和成本受控的发布步骤

| 步骤 | 产物与停止条件 | 新模型调用上限 |
|---|---|---:|
| 0. 旧题分析 | 用已有答卷生成按来源、题族、错误层级的通过矩阵；保留 60 道现有正式题不动。 | 0 |
| 1. 候选与裁判 | 写 8 道开发候选、4 道来源隔离留出；完成 v4 oracle、金标与定向反例、本地准入。若裁判或金标有歧义，修好再考虑模型调用。 | 0 |
| 2. 开发筛查 | 两模型、每候选一次直接生成。按题族看强模型是否还有信息、弱模型是否并非全零；一旦某题族两模型均全对，暂停该题族后续变体测试并先改题。 | 最多 16 |
| 3. 冻结留出 | 仅对通过步骤 2 的题族各取一份**不同来源**题，两个模型各一次。若新题与开发题显示相同错误层级且没有裁判问题，才认定有初步可迁移的难度证据。 | 最多 8 |
| 4. 一对一换题 | 从正式题里先替换已证实饱和、且同族覆盖重复的题，保留基础锚点。每加入一题退役一题，正式有效题始终约 60。保留版本化历史及旧分。 | 0 |

最多 **24 次新模型生成**，无默认重试、无 Judge、无全模型全题矩阵。若强模型在开发和留出继续接近全对，诚实报告该层级仍饱和，返回**新的来源和依赖设计**，不靠无限加字段或调低评分阈值硬造差距。两模型足以做首轮产品筛查；两模型每题只有 0/50/100% 三种样本通过比例，不能拟合可靠的项目反应曲线或宣称跨家族普适难度。

正式成绩保留基础题通过率、挑战题完整成功率与来源值准确率三栏，并记录题包版本。默认综合分若继续混合旧部分分和新二值题，应明确版本断点；旧分数不能与新题包分数直接排位比较。

## 六、实现落点

- `packages/core/src/evaluators/`：新增 `structuredContractV4`，读取私有 oracle，完成逐叶路径/证据/条件谓词评分；不修改 v1–v3 历史含义。
- `packages/core/src/contracts/registry.ts`、`packages/types/src/index.ts`：声明 v4 需求和分层指标；`apps/server/src/index.ts` 注册新评分器。
- `apps/server/src/routes/index.ts`：题目 API 对私有 oracle 不返回金标，正式运行只接收有版本哈希和来源清单的题；快照保存 oracle 引用与摘要。
- `data/pilots/` 与 `scripts/`：生成 source-disjoint 开发/留出题包、来源与许可证清单、金标和定向反例；发布脚本维持有效正式题数 60 并备份数据库。
- `apps/web/src/pages/EvalDetail.tsx`：并列显示基础覆盖、挑战完整成功率、逐叶来源值准确率、题族等权率和未测数量，避免单一平均分掩盖天花板。

**本轮完成标准**：先验证 v4 对同一题的合法替代答案、关键单缺陷答案和未知/无依据字段都能正确判分；再看两模型开发与独立留出是否产生一致、可解释的非满分信号。没有这些证据时，题目只能称候选，不能因“使用了权威方法”就标为高难。
