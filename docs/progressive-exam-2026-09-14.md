# 递进式数学试卷：分问交卷、限时给分

本版把限时完成能力纳入主分数：在规定预算内提交并答对的评分点累计得分，没完成的部分记零；超时、token 截断或后问答错均不抹掉前面已经取得的分数。基础设施失败保留已得分记录，但不生成可比较的整卷总分。

## 试卷结构

两道大题，每题 100 分、四小问，总计 8 小问。整卷 200 分归一化到 100 分，另外保留每道大题和每个评分项的原始得分。

| 小问 | 分值 | 单问时限 | 优化大题 | 有限域算子计数大题 |
|---|---:|---:|---|---|
| 1 | 10 | 180 秒 | 给定向量的目标值、费用、个数、可行性 | 像空间之和、商空间维数与同时消去性质 |
| 2 | 20 | 360 秒 | 构造可行解并计算目标值 | 不限制两核的算子对计数 |
| 3 | 30 | **1200 秒** | 按目标值门槛累计 10/20/30 分 | 增加 rank(A+B)=2 的计数 |
| 4 | 40 | **1200 秒** | 全局最优值和达到该值的见证 | 按同核/异核及和算子秩分类计数，六项分别给分 |

优化题沿用前轮的 16 变量实例，精确最优值 361；第三问的门槛为 217、289、343。它们在题面中明确给出，达到任一门槛需同时提交可行向量及准确的目标值。第二问可行向量值 15 分，准确目标值值 5 分。第四问单独考查精确最优性，前问得到的近似解分数不受影响。

独立枚举得到该实例共 4,642 个可行解，其中达到三个门槛的解分别有 1,987、140、4 个，全局最优解只有 1 个。这明确了目标逐步收紧的结构；它不是模型通过率估计，实际作答还取决于求解方法。

每问独立发起一次请求，只携带同一道大题此前已经提交的完整答案及对应题面，不携带隐藏思考、金标、得分或正误反馈。上一问答错或没交卷仍然进入下一问；两道大题之间重新开始上下文。本版是“分段限时交卷”，不是一条生成请求内把四问全部写完后才交卷，避免思考通道迟迟不输出最终答案时整题一起丢分。

单问提前完成即进入下一问，未用完时间不累积到下一问。单道大题的时限上界为 2940 秒，整卷为 5880 秒；这里的 **1200 秒是每个高难小问的上限**。

## 当前问发生截断时如何计分

每个评分点提交一个独立 JSON 对象，例如：

```json
{"item":"d","answer":3}
{"item":"m","answer":4}
{"item":"annihilated","answer":true}
```

允许逐项交卷，允许修改；同一评分项以最后一条完整、结构合法的记录为准。完整但内容错误的修改会覆盖旧答案；未闭合的 JSON 尾部不覆盖已交卷记录。不根据思考内容推测模型最终想交什么答案。

例如第一道大题前三问已得 60 分，第四问截断，则该大题保留 60/100。第二道大题末问的前两项已正确提交、第三项 JSON 只输出一半就超时，则前两项各得 7 分，未完成的第三项记零；前面三个小问的得分也全部保留。

服务正常结束但答卷为空，同样按未作答给零分，单独记录“没有提交评分项”。网络错误、错误模型返回、人工 STOP 等属于基础设施/运行中断，不能作为模型低分参与排名。

最初的工程验证沿用了 90,000 tokens 客户端上限，发现它会在 1200 秒前截断后，已主动停止该轮并保留全部原始记录。该轮两模型各记录四问，末问因人工停止标为运行中断，不产生整卷分数，也不与新轮择优合并。

完整限时试跑使用独立的 **budget-v2** 运行器：DeepSeek 请求上限为其官方 API 当前支持的 393,216 tokens；本机 Qwen 已核实总上下文为 120,000，请求输出上限设为 110,000，预留 10,000 给题面和已提交答案，运行前检查上下文配置未变。原始 SSE 大小保护同步从 64 MiB 放宽为 256 MiB，避免日志保护提前截断长回答。时间上限仍严格为每个高难问 1200 秒。[DeepSeek 参数说明](https://api-docs.deepseek.com/api/create-chat-completion/)

报告分别记录时间耗尽、token 截断和其他终止原因；Qwen 未返回 usage 时，实际 token 消耗记为未知，不把请求上限当成实际消耗。不同提供方的速度和模型容量属于本轮限时运行条件，不声称两模型用了相同算力。

## 验证与实测

六项新增测试覆盖：超时/截断后的保分、当前问完整评分项的部分得分、错误修订与不完整尾部、近似解分档、上下文只携带已提交答案、真正的流式 deadline 中断。全量 1,526 通过、213 跳过、0 失败；core 类型检查与构建通过。

独立金标核验：优化实例与前轮已获 HiGHS 全局最优证明的实例逐字段一致；基础代入用独立 Python 计算。有限域末问另用固定满射后的分类公式复核，六个金标依次为 208346040、416692080、0、0、6250381200、15000914880，与枚举完全一致。

当前只验证这两道大题上的分段评测机制。10/20/30/40 是事先冻结的分值，难度递进是设计目标；仍需用实测检查末问是否确实更难。小问之间有依赖和提示作用，8 个小问不能当成 8 个独立数学实例，也不能与前轮独立上下文、600 秒的整题得分作严格同条件比较。

限时试跑产物位于 `reports/progressive-exam-2026-09-14-v2/`，逐问保存请求、SSE、原始响应、状态、评分和增量提交。已中止的工程验证保存在同前缀 `-v1/` 目录。主分数按限时试卷分计算，另外报告完成情况和预算终止原因；不会因为出现截断而取消整个模型的有效试卷分。

完整实测及离线重判已经完成：DeepSeek 整卷 100 分，Qwen 40 分；Qwen 优化大题 30 分、算子计数大题 50 分。计分机制与本轮分差得到验证，但 DeepSeek 仍满分，Qwen 计数末问全对而中间两问错，严格难度递进尚未确立。两道大题的数量也不足以支持稳定排名或三个维度整体整改完成。当前候选未写入正式题库，未部署或推送 GitHub，也未修改历史成绩。详见[实测结论](progressive-exam-2026-09-14-results.md)及[逐问证据](progressive-exam-2026-09-14-evidence.json)。

## 复现

```powershell
pnpm eval:exam export reports/my-exam/development 20260915
pnpm eval:exam verify reports/my-exam/development
pnpm eval:exam prepare-run reports/my-exam/development reports/my-exam/deepseek deepseek-v4-flash
pnpm eval:exam run reports/my-exam/deepseek
pnpm eval:exam grade reports/my-exam/development reports/my-exam/deepseek/submission.json reports/my-exam/regraded.json
pnpm eval:exam:test
```

把提供方换成 `qwen-nvfp4` 可使用本机已有配置。时间与权重来自冻结题包；原始题包、运行计划和源代码摘要在每问前检查。所有导出、运行和重判结果使用新目录/文件，避免覆盖旧实验。
