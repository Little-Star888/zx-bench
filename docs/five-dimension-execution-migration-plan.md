## 已确认问题

### P0：评分契约和证据

1. 工具规则未消费：toolCallTrace.ts 未执行 requirements.calls、must_call、must_not、allowExtra、dependencies 等规则。registry.ts 已把部分字段标为声明但未消费。某些题退化为工具名和参数键存在性检查。
   - 离线探针 TC-CN-045：interval_minutes=999、priority=999 仍获规则 100 分，题库实际要求 30、5。
   - 离线探针 TC-CN-054：仅 session_search，没有 apply_fix，仍获规则 100 分。
   - 应把旧字段编译成显式断言；必需字段无实现时拒绝发布该执行题，不能静默省略或凭低覆盖分归一。
2. 调用顺序存在误判：toolCallTrace.ts 对每个工具只找第一次出现；TC-CN-011 的四次 create_reminder 被判顺序全部失败，探针规则分 67。这仅证明顺序轴有误，不说明探针的日期内容正确。
   - callMatch.ts 中一个 JSON actions 数组的所有动作使用同一个文本 index；探针 memory.read 和 memory.save 的 index 都是 0。
   - 应给调用独立 ordinal/callId，以出现次序匹配重复调用，再用依赖关系验证必须的先后顺序；允许无依赖动作交换顺序。
3. CLI 规则不能证明输出正确：CLI-CN-001 将 head -20 改为 head -1 仍获规则 100；base64、export/hash 又可能因提取白名单缺失误扣分。迁移为明确脚本提交字段，保留原样执行，不再用可执行名白名单猜答案。
4. 智能体状态评分读取模型描述：agentTrace.ts 用 expectedStateChanges 的文本模式判状态变化，不能证明记忆、日历或文件真的改变。新评分依据环境快照及事件。
5. 闭环完整证据未持久化：轨迹在 ModelResponse.agentLoop 中，orchestrator 返回与数据库保存路径未带出完整轨迹。Judge 收到最终文本而非完整工具执行记录。应先存逐轮工具记录、初末状态、终止原因和内容哈希，再允许离线重评。

以上探针均只调用确定性评分器，未调用语义裁判，不代表最终混合分或历史模型的实际行为。

### P0：闭环运行和业务语义

6. agentLoopTrace.ts 必要工具只检查工具名，未绑定订单、参数、调用顺序。既有探针 AL-CN-005 查询错误订单后仍可规则满分。
7. 终态检查应比较初态与末态：no_refund 当前检查所有退款记录为空；refund_issued 可能命中已有记录；no_state_change 只检查部分事件数组。应按题目定义保护的业务状态和本次事件增量判定，允许明确声明的消息/审计副作用。
8. retailRuntime.ts 的“当月退款次数”实际统计历史总次数；退款记录需时间戳及固定测试时钟。
9. 人工升级等同于审批完成；超期退款文本允许特批，运行时仍记录超期违规。应明确 requested/pending/approved/rejected，授权由环境事件产生，模型不能自行声明通过；同步修题面和断言。
10. 闭环工具白名单仅用于系统提示目录，执行分派没有再次验证；重复 CALL 在解析时被去重，掩盖重复执行倾向；宽松参数解析把非法 JSON 修补后执行。新协议严格校验工具可用性、参数类型和原始调用次数。
11. 错误、截断与轮次耗尽主要写入 evidence，未形成完整终止判定。无 CALL 就结束容易把无效回复当完成。增加 completed/awaiting_user/budget_exhausted/model_error/environment_error/cancelled 等状态，成功必须有环境证据。
12. hardTimeoutMs 逐轮传入、累计 usage 却保留最后一轮 latencyMs。应增加题级截止时间及剩余预算，区分模型等待、工具执行、环境准备耗时；多轮速度用全程一致分母。

### P1：评分口径与题目设计

13. 闭环最多 6 轮，效率轴也是 <=6 满分，无法区分效率。主指标用合规任务成功率，效率仅在成功任务之间比较，不奖励失败早停。
14. “人工”等末轮固定词造成沟通误扣分；若过程已经证实升级，应接受准确的完成说明。沟通裁判只评价表达与事实一致性，不推翻环境已验证的结果。
15. 安全题的文字拒绝与实际行为需要分别记录。拒绝文本不能抵消后续越权调用；环境拦截不能视为模型主动守规。保留 attempted/blocked/effective，并检查合法任务完成率，防止一律拒绝拿高分。
16. 工具题空字符串参数经常只检查键存在；类型正确与题意数值正确应各有断言。Catalog 的结构检查不能替代场景参数值检查。
17. should_not_directly 当前并入无条件禁止，不能表达“确认后允许”。HA-CN-045 要求先读后按缺失情况写入，静态动作清单却固定包含写入。改用显式条件、环境用户确认事件和状态前置条件。
18. 6 道 CLI 调查题的预设 explore 由程序代做，不能证明自主探索。执行版只提供必要入口，由模型选择探查操作，环境回传真实结果。
19. 现有闭环仅 5 道固定零售题；先迁移既有任务，再用少量正反成对状态、结果依赖和故障恢复变体校准。不要仅增加轮数、文本长度或强制某一种工具路径。

## 实施顺序及完成条件

### 1. 固定范围、版本和题目契约

- 输出 194 题迁移清单：旧版本、plan/script/live 模式、工具目录、初始化数据、允许动作、结果断言、保护状态、预算、失败归因。
- 审核 32 道安全题边界；将查询、拒绝、等待确认等正确结果明确列入成功条件。
- 固定新题包与镜像 digest、工具版本、评分器版本、fixture seed 和逻辑时钟；旧版历史结果留在旧版榜单。
- 完成条件：每个必需规则有验证器；未具备可判定 gold 的题暂不发布。

### 2. 修确定性规则与统一调用事件

- 修改 callMatch.ts、toolCallTrace.ts、agentTrace.ts、agentLoopTrace.ts 与 contracts/registry.ts。
- 每个调用含 callId、ordinal、tool、typedArgs、result、error、状态变化及违规信息；解析错误留痕，不能偷偷补参或合并调用。
- 区分旧计划文本与新执行事实；修复上述已复现的参数、漏步骤和重复调用问题。
- 完成条件：正确与等价解法通过；错值、漏步骤、错误对象、重复副作用等反例被检出。

### 3. 先补证据保存与离线重评

- 在 types、orchestrator、服务端结果保存和详情页贯通 traceArtifact 引用及哈希，保留完整轨迹与初末状态；大对象保存到运行制品目录，数据库存索引。
- Judge 获得受信任的执行摘要，原始工具内容明确作为不可信数据；程序断言决定可执行事实。
- 完成条件：同一轨迹离线重评可复现；旧结果没有轨迹时标“不可重放”，禁止编造轨迹。

### 4. 建设共享 Docker 会话执行层

- 复用 execution/containerRunner.ts 已有镜像预检、资源限制、守护进程故障判别和定向清理能力。
- 新增建议模块 execution/sessionRunner.ts：create → initialize → exec → snapshot/export → destroy。
- 现有 runInContainer 是一次性调用，finally 会删除容器和临时目录，不能直接承担多轮会话或终态制品采集。新增会话层与旧编程执行器并存，避免大范围重构。
- 每个题目变体使用独立可写工作区；多轮在同一会话保持文件和业务状态。镜像可复用，脏工作区不可跨题复用。
- 环境准备不计模型推理时间；镜像预先准备。设置总截止时间、单次命令时间、CPU/内存/进程/输出/磁盘预算，取消和超时必须收集可用证据后清理。
- 普通命令题禁外网；服务组合使用独立内部网络。无宿主业务目录、凭证或 Docker socket；评分标准和 gold 放在受信任控制端。
- 完成条件：会话可保留状态、提取制品并可靠清理，环境失败与模型失败可区分。

### 5. 建立两个环境适配器

- CLI 适配器：固定 Linux 工具链，支持文件、Git、权限、时间戳；按需附加数据库和本地 HTTP 服务。单次提交为完整脚本，多轮调查支持 shell 工具。
- 业务适配器：在容器内运行可重置的本地服务，承载 memory/calendar/order/approval/message 等状态；复用并修复 retailRuntime 业务逻辑。
- 对数据库、服务故障使用真实本地进程；邮件、资金、外发等仅写模拟账本/收件箱，不连接真实外部业务。
- 工具契约应有真实输入、返回值、状态变化、失败方式；不以固定成功字符串代替执行。故障注入按 fixture 固定，可测试超时但已成功、幂等重试、异步审批和状态变化。
- 完成条件：控制端可独立验证结果，候选输出不能伪造 PASS 或环境错误。

### 6. 分批迁移题目与评分

- 第一批 CLI 56：先 50 道脚本提交，再 6 道自主调查；为每题构造代表性输入和结果断言。数据未固定的旧文字题需要补 fixture，不能机械批量切换 grader。
- 第二批工具 56、智能体 45：按工具族复用环境；以必要依赖和终态评分，接受等价有效路径。
- 第三批安全 32：合法任务成功与越权尝试同时测量；注入内容放在真实工具响应中，用户确认由外部脚本产生。
- 同步完善已有闭环 5：目标绑定、时间窗口、审批、初末状态、错误处理、效率与沟通规则。
- 主指标为严格成功率；部分分只用于定位问题。关键任务/权限断言失败不得标成功，格式、解释或裁判高分不得补成成功。
- 完成条件：每道题有参考执行结果与至少一个能揭示核心错误的反例。

### 7. 最小验证、校准和发布

- 优先执行固定脚本/固定轨迹：无需调用模型。按共享执行器和业务工具族覆盖正常、错误、边界、取消/超时路径，不为每个薄封装重复造测试。
- 同一份单次脚本可复用到多组兼容 fixture，减少模型生成；交互策略遇到不同反馈必须重新运行，不能假称轨迹重放等于重新测量适应性。
- 选少量代表任务和至少不同系列的可用模型校准；先查假阳性、假阴性和结果稳定性，再逐批扩到 194 题。
- 数据库迁移保持兼容；新运行固定新题包、协议与环境版本。部署前检查活动评测，避免热替换正在运行的规则。
- 新旧执行模式分别呈现，显示任务成功率、权限尝试/生效违规、环境失败、耗时、调用数和 token。历史计划题不直接与执行题合榜。

## 实现结构

模型 → 统一协议适配器 → 会话控制器 → Docker CLI 环境 / Docker 业务服务

会话控制器同时向受信任制品存储写入调用事件、输出、终止原因及状态快照；容器外验证器读取这些证据产生断言结果，评分与详情页消费同一结果。

Docker 提供可复现执行与隔离，题目契约和验证器负责分数可信度。两部分需要共同完成。
